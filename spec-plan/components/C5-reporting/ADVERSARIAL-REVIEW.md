# C5 — Reporting — ADVERSARIAL REVIEW

**Reviewer persona:** the executive who will be fired if the report lied, the auditor who will sign their name under it, and the adversary who wants the report to look clean.

## 1. The report is where all the domain's honesty either holds or collapses
- **A1 — A report is a *summary*, and summaries are where lies hide.** Every honesty rule upstream (C2 `replay_completeness`, C4 confidence bands, C1 `indeterminate`) can be faithfully computed and then *aggregated away* at the report layer. "SC-IMG-001: 99.8% compliant" is a true-looking number that buries the 0.2% bypass and the 40% of evidence that was `insufficient`. The report's *aggregation choices* are an unaudited editorial act. **Severity: HIGH.** *Demand:* every headline aggregate MUST carry its denominator quality — "99.8% compliant **(of which 40% of evidence was best_effort/insufficient)**" — and the `insufficient`/`indeterminate` population MUST appear adjacent to every rollup, not in a footnote. A compliance percentage without an evidence-quality percentage is misleading by construction.
- **A2 — "No findings" is the most dangerous cell in any report.** A green coverage cell can mean "enforced and clean" OR "we never observed anything" OR "the source was down" OR "scope hid it." The spec acknowledges `installed_no_events` and "unavailable ≠ zero" (D-C5-05) — good — but a busy executive reads green as safe. **Severity: HIGH.** *Demand:* green/blank cells must be *typed* (enforced-clean vs no-observation vs unavailable vs out-of-scope) and visually distinct; an all-green report generated during a total outage must be impossible to mistake for compliance.

## 2. Scope filtering is a double-edged sword
- **A3 — Scope filtering can *manufacture* a clean report.** A user scoped to exclude the namespace where the bypass happened gets a clean report — legitimately, per their scope. But that clean report can then be *exported and presented* as evidence of compliance for a *broader* claim than the scope supports. **Severity: HIGH.** *Demand:* every export's signed manifest MUST embed the exact scope it covers, and the rendered report MUST state its scope prominently; a report scoped to one namespace must not be presentable as covering a tenant. The signature attests to scope, not just content.
- **A4 — Truncation notices get ignored.** "Results truncated by scope" as a notice is better than silence, but notices are dismissed/cropped in PDFs and emails. **Severity: MEDIUM.** *Demand:* truncation/unavailability must be reflected in the *counts themselves* (e.g. denominator marked partial), not only a banner that a PDF export might drop.

## 3. Signed-export theater
- **A5 — A signed PDF signs the *rendering*, not the *truth*.** The signed evidence package signs the NDJSON rows + manifest (good). But the PDF stakeholders actually read is a *separate rendering*; nothing forces the PDF to match the signed package. A doctored PDF with the right cover-page digest but altered body charts would pass a glance. **Severity: MEDIUM.** *Demand:* the PDF must be *derived deterministically* from the signed package and carry the manifest digest such that re-rendering from the package reproduces the PDF; or explicitly state the PDF is non-authoritative and only the package is evidence (D-C5-OQ1 leans this way — make it normative, not optional).
- **A6 — Verification requires the public key — does the auditor actually have a trustworthy copy?** "Verify with the published public key" assumes the auditor obtained the *genuine* key through a trusted channel. If they fetch it from the same platform that produced the report, a compromised platform serves a matching fake key. **Severity: MEDIUM (inherited from C2 key-trust).** *Demand:* the public key distribution/trust anchor must be out-of-band (org PKI, a transparency log — ties to C2 D7); the report must name the key's trust anchor, not just its id.

## 4. Cross-component contradictions
- **A7 — C5 R2 "renders C4 output, does not reconstruct" — but R2 also exposes a "Re-execute" button that calls E1.** Re-execution is replay; is that C5 reaching into E1, or C4's path? If C5's re-execute and C4's original reconstruction use different code paths or different bundle resolution, they diverge — and the auditor sees the *report* disagree with the *re-execution*, destroying trust at the worst moment. **Severity: HIGH.** *Demand:* re-execute MUST use the identical E1 entry point and the identical reconstructed synthetic event (by digest) that C4 stored; C5 passes through, never re-derives. Otherwise the auditor-independence feature becomes an auditor-distrust feature.
- **A8 — Four report types, three source components (C1/C3/C4), one schema (C2) — version skew across all of them shows up in C5.** If C3 finding schema vN and C5 expects vN-1, a report silently drops fields. C5 is the integration point where every upstream version mismatch surfaces as a *wrong report*. **Severity: MEDIUM.** *Demand:* C5 must validate source schema versions and refuse to render (or render with an explicit "schema mismatch" state) rather than silently dropping unrecognized fields — the opposite of the forward-compat "ignore unknown fields" rule, because in a *report* a dropped field is a lie.

## 5. Operational / abuse
- **A9 — Scheduled reports are fire-and-forget; a silently-failing weekly report means the audit committee assumes "no news is good news."** The spec logs+alerts a missed run (good) — but to whom, and is *that* alert itself reliable? **Severity: MEDIUM.** *Demand:* a missed scheduled report must produce a *positive* "report did not run" notice to the same distribution list, not just an internal log — silence must never be the failure mode for an audit-committee report.
- **A10 — "Top-10 denying policies" and similar aggregations invite gaming.** An operator who wants to look clean tunes policies from `deny` to `warn` (or `log_only`) — the real-time report's deny counts drop, looking like improvement, while enforcement actually weakened. The report rewards the wrong behavior. **Severity: MEDIUM.** *Demand:* the report must track enforcement *mode changes* (deny→warn) as a first-class drift signal (ties to C3 drift), so a drop in denies accompanied by a mode-weakening is flagged, not celebrated.

## 6. Prioritized defect list
| # | Defect | Sev | Fix |
|---|---|---|---|
| D1 | Aggregates bury evidence-quality; % compliant without % evidence-quality (A1) | HIGH | every rollup carries denominator quality; insufficient pop adjacent |
| D2 | Green/blank cells conflate clean vs no-observation vs unavailable (A2) | HIGH | type and visually distinguish every empty cell |
| D3 | Scoped clean report presentable as broader compliance (A3) | HIGH | signed manifest embeds + report states exact scope |
| D4 | Re-execute path may diverge from C4's stored reconstruction (A7) | HIGH | identical E1 entry + same synthetic event by digest |
| D5 | Signed package vs PDF rendering can disagree (A5) | MEDIUM | PDF deterministically derived from package + manifest digest, or PDF declared non-authoritative |
| D6 | Public-key trust anchor assumed (A6) | MEDIUM | out-of-band key distribution; name trust anchor (ties C2 D7) |
| D7 | Truncation notices dropped in exports (A4) | MEDIUM | reflect truncation in counts/denominators |
| D8 | Source schema skew silently drops report fields (A8) | MEDIUM | validate source schema versions; explicit mismatch state, don't drop |
| D9 | Missed scheduled report = silent "all good" (A9) | MEDIUM | positive "did not run" notice to distribution list |
| D10 | Deny→warn weakening looks like improvement (A10) | MEDIUM | track enforcement-mode changes as drift |

**Top must-fix:** D1 (a compliance percentage without an evidence-quality percentage is the single most likely way this platform misleads an executive), D2 (green-means-safe is how an outage gets reported as compliance), D4 (if the auditor's own re-execution disagrees with the report, the platform's central trust claim collapses in front of the one person it most needs to convince).
