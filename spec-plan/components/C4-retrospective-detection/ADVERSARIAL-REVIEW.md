# C4 — Retrospective Audit Detection — ADVERSARIAL REVIEW

**Reviewer persona:** forensic auditor + adversary who wants a bypass to stay invisible after the fact + a defense lawyer attacking the evidence's admissibility.

## 1. Reconstruction is fabrication wearing a lab coat
- **A1 — A reconstructed "violation" is the platform's *opinion* of what would have happened, presented as a finding.** C4 builds a synthetic input, replays it, and emits an "Audit-Derived Violation Report." But no enforcement engine ever actually denied this — C4 *infers* it would have. If the reconstruction is wrong (wrong bundle-at-time, wrong external-data value, missing a claim the policy keyed on), the platform asserts a violation that *never would have occurred*. In an audit or a dispute, "your tool reconstructed an input and decided I violated a control" is attackable evidence. **Severity: HIGH.** *Demand:* every audit-derived violation MUST be labeled as *reconstructed/inferred*, never presented with the same weight as a real recorded deny; the report must visibly distinguish "the engine denied this" (real C2 event) from "we infer the engine would have denied this" (C4 synthetic). The spec's confidence bands help but the *framing* in the report (C5) must not let a reader conflate the two.
- **A2 — `confidence=high` is too easy to reach and over-trusted.** "high = audit object + known bundle + re-resolvable external data." But re-resolving external data *at a historical timestamp* (e.g. image-signature status as of 3 weeks ago) is exactly the thing that may have *changed* — a signature could have been added/revoked since. Re-resolution can silently return *today's* answer, producing a `high`-confidence verdict that contradicts what the engine would actually have seen. **Severity: HIGH.** *Demand:* external-data re-resolution for historical replay MUST use the value *as of the action timestamp* (from C2's retained raw response, C2 §8.3), never a live re-fetch; if only a live value is available, confidence is capped at `medium` with an explicit `external_data_drift_possible` flag. This is the same trap as C1-A4 and must be solved identically.

## 2. The deep-bypass defense is aspirational
- **A3 — The third (inventory) view is the linchpin against a real attacker, and it may not exist.** C4's headline improvement over C3 is reconciling the *running fleet* (runtime scanner) so a bypass is caught even when the API audit was also disabled. But (a) PLAN R1 already admits the inventory source may not exist in the POC; (b) a runtime scanner is itself a *point in time* — a workload created and *deleted* during a bypass window (run a malicious job, tear it down) appears in *no* inventory snapshot and leaves the deep-bypass undetected. So the strongest claim ("did it *ever* get bypassed") is precisely the one C4 cannot fully honor. **Severity: HIGH.** *Demand:* be honest about the residual blind spot — C4 detects bypasses that left a *durable artifact* (audit row or surviving workload); ephemeral bypasses that left neither are undetectable by design. The §19.1 objective "detect workloads that bypassed enforcement" should be scoped to "detectable workloads," and the gap documented, not glossed.

## 3. Determinism and reproducibility
- **A4 — Auditor re-execution "ties out ≥95%" — what about the 5%?** DT-78 accepts ≥95% tie-out. But a 5% divergence between C4's stored verdict and an auditor's independent re-execution means *the same input replayed twice gives different answers* — which should be **impossible** for a deterministic replay (C2's whole premise). A 5% allowance quietly concedes non-determinism. **Severity: HIGH.** *Demand:* divergence should be ~0% for `complete`/well-formed replays; any divergence is a *defect* (non-deterministic policy, time-dependent external data, or a bundle-digest mismatch), each of which is independently diagnosable. The 5% is not "acceptable noise" — it's a list of bugs. Re-frame the SC: divergence triggers a mandatory root-cause, not a pass.
- **A5 — Bundle-at-time inference is a single inferred fact that the entire violation rests on.** "The bundle deployed to this scope at timestamp T" comes from a deployment/drift record. If that record is itself incomplete (the same drift problems C3 detects), C4 replays against the *wrong* policy and produces a wrong verdict with possibly-`high` confidence. C4 trusts the deployment record uncritically. **Severity: MEDIUM.** *Demand:* the inferred `policy_version` must be cross-checked against any *real* C2 decision events in the same scope/window (which carry the actual `policy_version`); a mismatch caps confidence and flags the inference.

## 4. Cross-component contradictions
- **A6 — C4 and C1 can disagree on whether a control was satisfied.** C4 emits a "governance-noncompliance event" → C1 renders `not_satisfied`. But C1 also independently evaluates coverage. If C4's window and C1's evaluation period differ, a control could be `not_satisfied` per C4's sweep but `partially_satisfied` per C1's rollup. **Severity: MEDIUM.** *Demand:* C1 verdicts cite the specific C4 finding ids; C4 sweeps and C1 evaluations must align on period boundaries or explicitly reconcile (mirrors C1-A5).
- **A7 — C4 "shares C3's detector library" but adds reconstruction/replay C3 lacks — versioning skew.** If the shared library is versioned and C3 runs vN while C4 runs vN-1 (or vice versa), a bypass C3 alerted on live may not reproduce in C4's sweep, or vice versa — the "cannot diverge" guarantee (D-C4-01) silently breaks on version skew. **Severity: MEDIUM.** *Demand:* C3 and C4 must pin and report the *same* detector-library version for a given comparison; a sweep records the library version so its results are reproducible and comparable to live alerts.

## 5. Abuse / evidentiary
- **A8 — The `recommended_remediation` string is unstructured and could be wrong/auto-generated nonsense.** §17E.3 requires it; if it's a templated guess ("rotate base image") that doesn't fit the actual violation, it undermines the report's credibility. **Severity: LOW.** *Demand:* remediation should be derived from the control's defined remediation (A1), not free-text invention.
- **A9 — Low-confidence violations "excluded from auto-totals pending confirmation" — who confirms, and is the confirmation audited?** An insider could refuse to confirm low-confidence violations that implicate them, keeping them out of totals forever. **Severity: MEDIUM.** *Demand:* unconfirmed low-confidence violations must still be *visible* (a backlog with age), not silently absent; confirmation/dismissal is an audited, chained action (mirrors C3-A8).

**Top must-fix:** D1 (a historical replay that uses present-day external data is *not* a faithful replay — it defeats the entire premise), D3 (the platform must not claim to detect bypasses it structurally cannot), D4 (a deterministic replay that disagrees with itself 5% of the time is broken, and calling it a tolerance hides bugs).
