# C2 Audit Event Schema — `c2.audit-event/1.0-rc` (RECONCILED)

**Status:** **UN-FROZEN → RELEASE CANDIDATE.** Supersedes the prematurely-frozen
`c2.audit-event/1.0` (C2 SPEC §3.13). This document lands the **build-blocking subset** of
`CROSSCUT-ADVERSARIAL §4` (XD-1, XD-2, XD-3, XD-8, XD-11, XD-12, XD-13) and the
`INTER-DOMAIN-CONTRACTS` overrides (OV-1, OV-3, OV-4) and `DATA-MODEL` reconciliations
(R1, R7) that touch the audit event. After review this becomes `c2.audit-event/1.0` (final).

**Authoring rule honored:** v1.x is **additive-only** (N-C2-FWD). Every change below is one of:
(a) a *semantics* change to an existing field, (b) a *required-ness/conditionality* tightening,
or (c) a clearly-marked **NEW additive optional field**. **No frozen field is removed or
repurposed.** The two enum reshapes (`decision`→`disposition`, value-capture) are done so that
the *old field name is retained as a deprecated alias* wherever a consumer might still read it,
so an ignore-unknown-fields consumer of 1.0 keeps working against a 1.0-rc producer.

**Reconciler:** cross-cutting (staff, build-blocking landing). **Date:** 2026-05-30.

## 1. The action-model split — disposition vs obligations (XD-3 / XD-11 / OV-3)

### 1.1 The defect being fixed
Frozen v1.0 field 9 `decision` was a **flat enum** that mixed two orthogonal axes:

- the **exclusive verdict** (`allow`/`deny`/`suspend_pending_approval`/…), of which exactly one
  is true; and
- **co-occurring effects** (`mutate`, `annotate`, `notify`, `quarantine`, …), of which several
  can be true at once.

Because `mutate` sat as a *sibling* of `deny`, a **deny-that-also-mutated** (or, more commonly,
an **allow-that-mutated-and-notified**) had no representation: you could record `mutate` OR
`deny`, never both. `action_performed` (field 15) was a second, un-reconciled effect enum, and
B4's 13-action set, C2's `decision`, C2's `action_performed`, and E3's verbs were **four closed
vocabularies that disagreed** (XD-11). The single linear precedence (B4-R7) only makes sense
*within the disposition axis*.

### 1.2 The fix — two dimensions, separate field homes
Per `INTER-DOMAIN-CONTRACTS §5` (Contract 5) and OV-3, the model is split into:

**Dimension A — `disposition`** (NEW field 37, exactly one per `policy.decision`):
```
allow | deny | warn | suspend_pending_approval | require_approval | unknown
```
The B4 single linear precedence (`deny > require_approval > quarantine > … > allow`) is
**retained but re-scoped to resolve the disposition axis only** when multiple controls fire.

**Dimension B — `obligations[]`** (NEW field 38, zero-or-more), drawn from the **closed** B4
obligation set (the canonical taxonomy minus the pure verdicts):
```
mutate | generate | cleanup | quarantine | suspend | require_approval |
require_scan | notify | annotate | exception
```
(`audit` is always implied and is not emitted.) Each obligation’s **concrete realized effect**
is recorded in `action_performed` (field 15, re-scoped) and, for `mutate`, in `mutation_diff`
(field 16).

### 1.3 Canonical reconciliation table (frozen, mirrors Contract 5 §5.3)

| B4 13-action | `disposition` (field 37) | `obligations[]` (field 38) | realized `action_performed` (15) |
|---|---|---|---|
| `allow` | `allow` | — | `log_only` |
| `deny` | `deny` | — | `block` |
| `warn` | `allow` | `warn`/`notify` | `annotate`/`log_only` |
| `mutate` | `allow` | `mutate` | `mutate` (+ `mutation_diff`) |
| `generate` | `allow` | `generate` | `annotate`/`log_only` |
| `cleanup`/`delete` | (controller verdict) | `cleanup` | `block`/`log_only` |
| `quarantine` | (controller) | `quarantine` | `block` |
| `suspend` | `suspend_pending_approval` | `suspend` | `route_for_approval` |
| `require_approval` | **`deny`** (at admission) | `require_approval` | `route_for_approval` |
| `require_scan` | per result | `require_scan` | `log_only` |
| `notify` | (inherits) | `notify` | `log_only` |
| `annotate`/`label` | `allow` | `annotate` | `annotate` |
| `exception` | `allow` | `exception` | `log_only` |

E3’s product verbs **map onto** this canonical set (they do not extend it): `detect→notify`,
`alert→notify`, `fail build→deny`, `attach evidence→annotate`(obligation), `require review→
require_approval`, `require MFA→require_approval`(obligation), `clear hold→` disposition
transition. C2 enums are **regenerated from** the single B4 taxonomy — one vocabulary, derived
once (XD-11).

### 1.4 Back-compat (critical, additive-only)
- `disposition` is **NEW**; `decision` (field 9) is **retained** and, for `policy.decision`
  events, MUST carry the *same value* as `disposition` for the six values both share. A 1.0
  consumer that only reads `decision` still gets the verdict.
- The old `decision` value `mutate` is **never emitted** by a 1.0-rc producer (mutate is now an
  obligation, and the disposition is `allow`). This is the one behavioral change a 1.0 consumer
  sees: a previously-`decision:mutate` event now reads `decision:allow` + `obligations:[mutate]`.
  This is correct — it never *was* a verdict. Documented in the migration note (§6).
- `obligations[]` is a NEW optional field; a 1.0 consumer ignores it (N-C2-FWD). Consumers that
  need to render "denied AND mutated AND notified" upgrade to read `disposition` + `obligations`.

## 2. External-data value capture — unambiguous and owned (XD-1)

### 2.1 The self-contradiction being resolved (§8.3 vs §5.2)
v1.0 was internally complicit in not capturing values:
- §8.3 / N-C2-402 / D-C2-05 **claim** the store retains the *raw external-data provider
  responses*.
- But field 27 `value_ref` was **OPTIONAL**, and §5.2 listed "value unavailable but
  re-resolvable" as a **normal `best_effort` path** — a standing escape hatch that legitimized
  *not* capturing the value.

Net effect: the flagship "require signed image" example replayed as `best_effort` (not
`complete`), because no producer was obligated to emit the `image-signature-status` **value**,
and §5.2 said that was fine. The platform's #1 differentiator failed on its own demo.

### 2.2 The fix — value capture is a MUST for volatile providers
1. **`value_ref` (field 27) becomes CONDITIONALLY REQUIRED** whenever the policy-dependency
   catalog (§4.2) marks the consulted provider **volatile / non-re-resolvable** (signature
   status, CVE feed, time-varying allow-lists). For catalog-marked **stable** providers
   (re-resolvable deterministically by version), value capture stays optional and the §5.2
   re-resolvable path remains valid.
2. **Producers MUST emit the value at source.** B1/B5 decision evidence MUST capture the
   external-data **value** the verifier returned at decision time (`decision.evidence`
   extension), not merely the version/digest. C2 stores it in its CAS (§8.4) and points
   `value_ref` at it (`cas://blobs/sha256:…`).
3. **C2 owns the content-addressed external-data snapshot store** (it already owns CAS via
   §8.4). This is now a first-class store, not an afterthought.
4. **§5.2's re-resolvable escape is NARROWED.** For a **volatile** provider, a missing captured
   value is **`insufficient`**, never `best_effort`. The §5.2 "re-resolvable ⇒ best_effort" path
   applies **only** to catalog-marked **stable** providers.
5. New reason code `external_data_value_uncaptured:<provider>` (added to §5.5) is emitted when a
   volatile provider's value is absent.

### 2.3 Result: the flagship image-signing example now replays `complete`
With B1/B5 emitting the `image-signature-status` value and C2 storing it under `value_ref`, the
canonical Gatekeeper deny (§3.8 in v1.0) satisfies every §5.1 `complete` precondition — the
value, not just the version, is captured. See the revised example in §5.

## 3. `jwt_claims_completeness` producer→scorer→consumer wiring (XD-12)

### 3.1 The orphan being adopted
Field 19 `jwt_claims_completeness` (`full | partial | reconstructed`) is a **precondition for
`replay_completeness=complete`** (§5.1) and the **baseline C3 DT-31 JWT-drift detects on**. But
**no one set it**: D1 (the `jwt_claims` producer) never emitted the completeness sub-state, and
the C2 normalizer cannot know whether D1 captured *all* policy-consulted claims without (a) the
policy-dependency catalog and (b) the set of claims D1 actually captured. Result: either mass
under-reporting (defaults absent ⇒ never `complete`) or a **silent false-`complete`** that
dropped a claim the policy used.

### 3.2 The fix — an explicit D1↔C2 contract
- **Producer (D1):** the D1 normalization output MUST carry **`jwt_claims_captured[]`** (NEW
  field 39) — the exact set of claim names captured at decision time. The Keycloak
  token-issuance-reconstruction path MUST stamp its events so C2 knows the claims were *rebuilt*,
  not captured live.
- **Scorer (C2):** the C2 normalizer **computes** `jwt_claims_completeness` by diffing
  `jwt_claims_captured` against the **pinned catalog's** required-claim list for
  `(policy_ref, policy_version)`:
  - captured ⊇ required, live capture → `full`;
  - captured ⊂ required (some required claim missing) → `partial`;
  - claims rebuilt from a Keycloak issuance event joined by `sub`+time → `reconstructed`.
  - **Catalog absent ⇒ `partial`, never `full`** (honesty tenet, mirrors D-C2-06).
- **Consumer (C3):** DT-31 JWT-drift detects against the now-trustworthy field; `partial`/
  `reconstructed` correctly caps `replay_completeness` at `best_effort` (§5.2).

### 3.3 The two `partial`s stay distinct (R1)
`jwt_claims_completeness=partial` is a **different field** from replay `best_effort`. The replay
middle state was renamed to `best_effort` **precisely** to end this collision (D-C2-01 / R1 /
OV-1); `jwt_claims_completeness` keeps `partial` unchanged. A `jwt_claims_completeness=partial`
maps **into** `replay_completeness=best_effort` (reason `jwt_partial`), never the reverse.

## 4. `partial → best_effort` rename, kept distinct from JWT `partial` (R1 / D-010 / OV-1)

- `replay_completeness` value set is **frozen** as **`complete | best_effort | insufficient`**.
- `partial` is a **deprecated ingest/query alias** of `best_effort`: the normalizer accepts
  `partial` on ingest and rewrites it to `best_effort`; the consumer API (§10.1) accepts
  `partial` as a query synonym. E1's `ReplayEventV1` adapter performs the `partial→best_effort`
  normalization (D-E1-03 / OV-1).
- **Distinct from JWT:** `jwt_claims_completeness=partial` (field 19) is untouched. Wherever a
  source SPEC says `replay_completeness=partial`, read `best_effort`; wherever it says
  `jwt_claims_completeness=partial`, leave it.

## 5. `correlation_id` resolution — retry-stable logical flow (XD-8 / OV-4)

### 5.1 The defect
`correlation_id` was anchored to the **AdmissionReview UID**, but Kubernetes mints a **fresh UID
per request**, and an approval flow has **two** admissions for **one** logical request: (1) the
original deny-with-approval-required, and (2) the post-approval **retry**. The naive rule gave
the deny (id X) and the approved retry (id Y) **different** ids — fragmenting the governance
transaction, so C4 saw the approved deploy as an unpaired (bypass-looking) event.
`parent_correlation_id` was documented only for synthetic replay, not approval retry.

### 5.2 The fix (frozen resolution per OV-4 / Contract 6 §6.2)
1. **`correlation_id` (field 3) is the retry-stable logical-flow id.** For approval flows it is
   anchored to the **`PolicyApprovalRequest` identity** (the CR name, derived deterministically
   from `(controlId, resourceRef, requestedBy)`), so the original deny and the retry-admit share
   one id. For ordinary single-admission flows it remains the AdmissionReview UID.
2. **The per-admission AdmissionReview UID is demoted to a secondary id**, recorded **per-event**
   in `engine_context.gatekeeper.admission_review_uid` (it was already there in v1.0 — now it is
   *explicitly the home* of the per-admission UID, never the cross-event join key for approval
   flows).
3. **`governance_transaction_id` (NEW field 40)** is the explicit, stable id that survives the
   retry, carried alongside `correlation_id` for flows where a single stable id alone is
   insufficient. B4 mints it at approval-request time; B5 propagates it on the retry; C2 carries
   it. `parent_correlation_id` (field 4) MAY additionally link a retry event back to the original
   deny, but the **default/preferred** mechanism is the stable `PolicyApprovalRequest`-anchored
   `correlation_id` + `governance_transaction_id`.
4. **Cluster-scope** the id to defeat federated collision (DC-11 / XD-19 coupling).

> **Net rule (frozen):** *Within one logical request — including across an approval
> deny→approve→retry cycle — there is exactly ONE `correlation_id` and ONE
> `governance_transaction_id`. Per-admission AdmissionReview UIDs are recorded as secondary ids
> in `engine_context`, never as the cross-event join key.*

```
         request_object, external_data_refs, replay_completeness_reasons,
         confidence_level
         [decision is retained as a deprecated alias of disposition; it does not
          add to the C count — disposition is the canonical C field, decision mirrors it]
O  (9):  parent_correlation_id, obligations, action_performed, jwt_claims_captured,
         governance_transaction_id, catalog_version, engine_context, signature,
         decision (deprecated alias)
```
**14 R + 18 C + 9 O = 41.** All 36 v1.0 fields retained; 5 net-new additive optional fields
(`obligations`, `jwt_claims_captured`, `governance_transaction_id`, `catalog_version`, plus the
`decision`→`disposition` pairing where `disposition` is the canonical C and `decision` becomes
the O alias).

## 7. Revised invariants

**Carried forward unchanged:** N-C2-FWD (ignore unknown fields / tolerate unknown enums),
N-C2-100..105 (normalizer projection/retention/scoring/correlation/canonicalize/idempotency),
N-C2-200..203 (correlation anchors), N-C2-300..304 (canonicalization, hash chain, signed Merkle
checkpoints, redaction-aware integrity, signed export envelope), N-C2-400..402 (append-only,
scope-aware access, raw-event retention), N-C2-500..501 (OCSF one-way), N-C2-SYNTH (synthetic
capped at `best_effort`), N-C2-NOPROMOTE (no silent promotion).

**Amended / new invariants:**

- **N-C2-DISP (new, XD-3/OV-3):** every `policy.decision` event MUST carry exactly one
  `disposition`. `obligations[]` is a set drawn solely from the closed B4 obligation vocabulary.
  `decision` MUST equal `disposition` for the shared values and MUST NOT carry `mutate`.
- **N-C2-EDV (new, XD-1):** when the pinned catalog marks a consulted provider
  volatile/non-re-resolvable, `external_data_refs[].value_ref` MUST point to a captured value in
  CAS. A volatile provider with no captured value ⇒ `replay_completeness=insufficient`
  (reason `external_data_value_uncaptured:<provider>`), **never** `best_effort`. The §5.2
  re-resolvable→`best_effort` path applies **only** to catalog-marked stable providers.
- **N-C2-JWTC (new, XD-12):** `jwt_claims_completeness` is **computed by the C2 scorer** from
  `jwt_claims_captured` ∩ pinned-catalog required claims. The normalizer MUST NOT default it to
  `full`. Catalog absent ⇒ `partial`.
- **N-C2-LB (amended, XD-2):** the stored `replay_completeness` is a **per-event lower bound for
  the deciding bundle**. E1 MUST recompute per simulated bundle; that recomputation is
  authoritative for the run. On divergence, **conservative-label-wins**
  (`insufficient > best_effort > complete`); a live-vs-replay divergence on a stored-`complete`
  event is a **finding**, not an accepted tolerance (couples XD-15).
- **N-C2-CAT (new, XD-13):** the policy-dependency-catalog version is pinned per
  `(policy_ref, policy_version)` in `catalog_version` and bound into `content_hash`. At runtime,
  the bundle's **observed** external-data/claim reads are compared against the catalog; on
  mismatch the event is downgraded to `best_effort` with reason `catalog_stale`. C3 input-
  equivalence derives its relevance set from the **same pinned** catalog.
- **N-C2-TXN (new, XD-8/OV-4):** within one logical request, including across an approval
  deny→approve→retry, there is exactly ONE `correlation_id` and ONE
  `governance_transaction_id`. Per-admission AdmissionReview UIDs live in
  `engine_context.gatekeeper.admission_review_uid`, never as the cross-event join key.

## 9. Migration note — `c2.audit-event/1.0` → `1.0-rc`

**Posture:** additive-only within v1.x; consumers ignore unknown fields (N-C2-FWD). 1.0-rc is a
release candidate; on review acceptance it becomes the final `c2.audit-event/1.0`.

**For producers (normalizer, B1/B5, D1):**
1. Emit `disposition` (NEW) on every `policy.decision`; keep `decision` equal to it; stop
   emitting `decision:mutate` (emit `disposition:allow` + `obligations:[mutate]`).
2. Emit `obligations[]` from the closed B4 set; record the realized effect in `action_performed`.
3. B1/B5: capture the external-data **value** for catalog-volatile providers; C2 stores it and
   sets `value_ref` (now conditionally required).
4. D1: emit `jwt_claims_captured[]`; the Keycloak-reconstruction path stamps `reconstructed`.
5. C2 normalizer: compute `jwt_claims_completeness` from captured ∩ catalog; pin `catalog_version`
   and bind it into `content_hash`; mint/propagate `governance_transaction_id`; record the
   per-admission UID only in `engine_context`.

**For consumers (C1, C3, C4, C5, E1, F1, F2, F4):**
1. **No break for read-only-of-known-fields consumers** — all 36 v1.0 fields remain.
2. Consumers needing "denied AND mutated AND notified" MUST upgrade from reading `decision`
   alone to reading `disposition` + `obligations[]`. (A consumer that only reads `decision`
   still gets the verdict; it just won't see co-occurring effects.)
3. E1 MUST recompute `replay_completeness` per simulated bundle (N-C2-LB) and apply
   conservative-label-wins; treat the stored flag as a lower bound only.
4. C3 DT-31 JWT-drift now detects against scorer-computed `jwt_claims_completeness`; relevance
   sets derive from the pinned `catalog_version`.
5. C4 reconstruction MUST follow the retry-stable `correlation_id`/`governance_transaction_id` so
   the approved retry is no longer seen as unpaired.
6. The deprecated `partial` alias for `replay_completeness` continues to be accepted on ingest
   and as a query synonym (no consumer change required).

**Content-hash impact:** because `catalog_version` is now bound into `content_hash`, 1.0-rc event
hashes are computed over the new field set. Re-normalized 1.0 events get a new `content_hash`
(expected — re-normalization always appends a new event with lineage to the superseded one,
N-C2-105; the chain is never rewritten).

**Re-freeze gate:** this RC re-freezes to final `c2.audit-event/1.0` only after the build-blocking
checklist (`BUILD-BLOCKING-FIXES.md`) items XD-3, XD-11, XD-1, XD-2, XD-13, XD-12, XD-8 are
landed and their acceptance criteria pass. XD-5 and XD-9 gate the D2/B4 contracts respectively
and are tracked there, not in the C2 field set.
